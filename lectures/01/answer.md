- 気づき・疑問：
    - 基礎
        - 「temperature 0 なら毎回同じ答え」と思っていたが、そうならなかった。思考トークン（`thoughts_token_count`）は使われていなかったので、サーバー側の要因（バッチ処理や GPU の浮動小数点演算の順序など）で確率がわずかに変わり、最初の数トークンで別の書き出しを選ぶと、そこから先がまったく違う文章になるのだと考えた。
        - temperature 2.0 にしても、文章が崩れたり大きく話がそれたりはせず、むしろ回答どうしが似ていた。3回ずつでは試行が少なく、文字列の類似度も「言い回しの違い」を測るだけの粗い指標なので、温度の効果をはっきりとは言えない。モデル側で temperature の効き方が調整されているのかもしれない（疑問）。
        - どの温度でも正解には近づかなかった。temperature が変えるのは「どの言い方を選ぶか」のばらつきだけで、**モデルが知らない知識は補えない**。正しく答えさせるには、第3回のように用語集を検索させるなど、外から知識を与える必要がある。
    - 実装
        - LLM 自体は前のやり取りを覚えておらず、`chat` オブジェクトが毎回これまでの履歴を全部送っているだけだった。そのため、会話が長くなるほど入力トークンが増え、料金・応答時間・無料枠の消費も増える。長い会話では、古い履歴を捨てるか要約する工夫が必要になりそう。
        - 実装中に、`genai.Client` を関数の中で作って `chat` だけを返すと、関数を抜けたときに Client が破棄されて接続が閉じ、2回目以降の送信が `RuntimeError: Cannot send a request, as the client has been closed.` で失敗した。`chat` は Client の接続を借りているだけなので、Client は `main()` で持ち続けるように直した。
        - 疑問：API エラー（レート制限など）が起きたときは今は終了するが、履歴を残したまま待って再送できるようにしたほうが使いやすいか。
    - 発展
        - **応答時間は、ほぼ「生成したトークン数」で決まる。** 長い回答ではどのモデルも速度がほぼ一定だった（3.5-flash-lite 約195、3.5-flash 約135、3.1-flash-lite 約105 トークン/秒）。「一言」では速度が大きく下がった。これは、生成の量に関係なくかかる固定の待ち時間（通信や処理の開始など、3.5-flash-lite で1秒弱）の割合が大きくなるためだと考えた。
        - **`gemini-3.5-flash` が遅いのは主に「考えている」から。** 出力は flash-lite とほぼ同じ量なのに、長い回答では出力の1.4〜1.9倍の思考トークンを使い、応答時間は約3.5〜5.5倍になった。「一言で」と頼んでも思考は 241〜429 トークン使われた（出力 31 トークンの約12倍）。思考トークンも出力として課金される（と理解している）ので、見えている回答の長さだけでは料金も時間も見積もれない。なお、講座固有の質問では思考が最も多かった（平均1218）が、答えはほかのモデルと同じく一般論で、正解には近づかなかった。考えても、知らない知識は出てこない。
        - **入力トークン数はモデルが変わっても同じ**（7 / 21 / 14）だった。この3モデルは同じトークナイザーを使っているようだ。
        - **`gemini-3.1-flash-lite` は応答時間のばらつきが大きかった。** 一言の質問で 2.7〜25 秒（25 秒は1回だけの外れ値）、503 や記録できなかった失敗もあった。混雑の影響を受けやすい時間帯だったのかもしれない（1日分しか測っていないので不明）。
        - **レート制限との関係**
            - RPM（1分あたりのリクエスト数）は**回数**で数える。`1+1は？` のような 10 トークンの質問でも1回分を消費し、1秒弱で返ってくる 3.5-flash-lite では、待ち時間なしだと12〜14秒で上限に達した。短い質問をたくさん送る使い方では、まず RPM が上限になる。
            - 逆に、1回に12〜14秒かかる 3.5-flash を1つずつ順番に呼ぶなら、1分に4〜5回しか送れないので RPM には届きにくい。モデルの速さによって、どの制限が問題になるかが変わる。
            - TPM（1分あたりの**入力**トークン数）は量で数える。会話モードでは、5往復目で1回の入力が 3,104 トークン、5往復の合計が 7,304 トークンになった。会話が長いほど、回数は少なくても TPM を早く消費する。
            - 第3回以降のエージェントは、1つの質問の中で LLM を何度も呼び、そのたびに履歴やツールの結果を送る。RPM と TPM の両方を「1つの質問 = 1回」より何倍も早く使うので、待ち時間やリトライ、履歴の要約を組み込む必要がある。
            - 制限は API キー単位ではなく**プロジェクト単位・モデル単位**でかかる（`quotaId` と公式ページより）。キーを増やしても回避できないが、制限に達したらモデルを切り替える（3.5-flash-lite → 3.1-flash-lite など）という逃げ道はある。
        - 疑問
            - 上限は15なのに、2回とも16回目まで成功した。また、「47秒後に再試行」と言われたのに13.6秒で回復した。きっちり「1分ごとにリセット」ではなく、時間とともに少しずつ枠が戻る仕組み（スライディングウィンドウやトークンバケット）なのかもしれない。
            - 1日あたりの上限（RPD）は、公式ページに数値がなく AI Studio で確認するようになっていたため、今回は確かめていない。RPD は太平洋時間の午前0時（日本時間の16時か17時）にリセットされる。
            - 計測は1日・各3回だけなので、時間帯による混雑の差は分からない。
    - 総括
        - 素の LLM は、知らないことでも「一般的には〜」ともっともらしく答え、temperature を変えてもその性質は変わらなかった。会話の「記憶」もモデルの能力ではなく、アプリ側が履歴を送り直す仕組みで実現されていた。さらに、応答時間・料金・レート制限は、見えている回答の長さではなく「送ったトークン（履歴を含む）」「生成したトークン（思考を含む）」「呼び出した回数」で決まる。LLM の外側（履歴の管理や知識の与え方）をどう設計するかが AI エンジニアリングの中心だと感じた。
